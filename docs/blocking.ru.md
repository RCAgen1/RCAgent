# Причины недоступности сервиса: полная классификация

Документ охватывает все значимые причины, по которых сервис может быть недоступен: от технических сбоев и инфраструктурных отказов до интернет-цензуры. Российские блокировки вынесены в отдельный раздел, остальные разделы универсальны. Для каждой причины описаны технические сигналы, наблюдаемые обсерверами, и подходы к классификации.

## 1. Инфраструктура блокировок в России

### 1.1 Реестр РКН

Роскомнадзор ведёт реестр запрещённых ресурсов (`eais.rkn.gov.ru`). Провайдеры обязаны подключиться к нему и применять блокировки в реальном времени. Реестр содержит записи трёх видов:

- по IP-адресу или подсети
- по домену или URL
- по автономной системе (ASN)

### 1.2 ТСПУ (Технические Средства Противодействия Угрозам)

Введены законом о «суверенном интернете» (149-ФЗ, 2019). Оборудование устанавливается на стороне провайдера, но управляется централизованно из РКН. Это DPI-система, способная:

- анализировать трафик до уровня L7
- блокировать по сигнатурам протоколов (Tor, WireGuard, OpenVPN и др.)
- замедлять трафик (throttling) без полной блокировки
- блокировать по SNI в TLS ClientHello
- подменять DNS-ответы

ТСПУ — главный инструмент «умных» блокировок начиная с 2021 года.

## 2. Типы блокировок

### 2.1 Блокировка по IP

**Как работает.** Провайдер добавляет IP-адрес (или подсеть) в ACL или null-route. Все пакеты до этого адреса отбрасываются или возвращают TCP RST.

**Кто применяет.** Все провайдеры через реестр РКН. Самый распространённый и грубый метод.

**Проблемы метода.** Коллатеральный ущерб: блокировка одного IP затрагивает все сайты на shared-хостинге. Именно это произошло с попыткой заблокировать Telegram в 2018 — были заблокированы миллионы IP Amazon и Google.

**Признаки:**

- TCP SYN уходит, SYN-ACK не приходит (timeout) или приходит TCP RST
- Traceroute теряет пакеты на последнем хопе внутри AS провайдера или обрывается раньше
- DNS-резолюция успешна, проблема на сетевом уровне
- Поведение одинаково по HTTP и HTTPS

---

### 2.2 Блокировка по DNS

**Как работает.** Провайдер конфигурирует свои DNS-резолверы возвращать:

- `NXDOMAIN` (домен не существует) — чаще всего
- IP заглушки (страница-блокировщик провайдера или РКН)
- `0.0.0.0` / `127.0.0.1`

Используется как самостоятельный метод или в связке с IP-блокировкой.

**Признаки:**

- Запрос к DNS провайдера (`resolv.conf`) возвращает NXDOMAIN или посторонний IP
- Тот же запрос к `8.8.8.8` или `1.1.1.1` возвращает правильный IP
- HTTP-соединение к полученному от провайдера IP ведёт на страницу-заглушку
- DNSSEC-валидация проваливается (если провайдер подменяет ответ)

**Страница-заглушка РКН.** Стандартная страница содержит текст «Доступ к ресурсу ограничен» и ссылку на реестр. Заглушки провайдеров отличаются, но чаще всего содержат слова `rkn`, `block`, `zapret` в теле или заголовках.

---

### 2.3 DPI-блокировка по SNI (TLS)

**Как работает.** В TLS ClientHello клиент отправляет SNI — hostname в открытом виде. ТСПУ перехватывает соединение, читает SNI, и если домен в реестре — отправляет TCP RST обоим участникам соединения.

Это позволяет блокировать конкретный домен на shared IP (в отличие от IP-блокировки).

**Признаки:**

- TCP-соединение устанавливается (SYN-ACK получен)
- TLS ClientHello уходит
- Приходит TCP RST вместо ServerHello (или соединение закрывается без ответа)
- То же IP с другим SNI (или без SNI) — работает
- Наблюдается на порту 443

**ESNI/ECH.** Зашифрованный SNI скрывает hostname от DPI. ТСПУ в ряде случаев блокирует ECH-трафик полностью (как неизвестный протокол).

---

### 2.4 DPI-блокировка по HTTP Host

**Как работает.** Для незашифрованного HTTP (порт 80) ТСПУ читает заголовок `Host` и блокирует, если домен в реестре.

**Признаки:**

- TCP-соединение устанавливается
- HTTP GET уходит
- Приходит TCP RST или HTTP 403/302 на страницу-заглушку
- HTTPS к тому же домену может работать (или нет — зависит от наличия SNI-блокировки)

---

### 2.5 Блокировка по URL

**Как работает.** ТСПУ анализирует полный URL в HTTP-запросе и блокирует конкретный путь, не весь домен.

**Пример.** `site.com/banned-page` заблокирован, `site.com/other` — нет.

**Признаки:**

- Конкретный URL возвращает RST или редирект на заглушку
- Другие пути на том же домене работают
- Специфично для HTTP (не HTTPS, там URL не виден DPI)

---

### 2.6 Блокировка по ASN / BGP Blackholing

**Как работает.** Провайдер или вышестоящий оператор анонсирует null-route для всей автономной системы (ASN) или конкретной подсети через BGP. Трафик направляется в никуда.

**Используется против.** Зарубежных хостинг-провайдеров, CDN, крупных платформ.

**Признаки:**

- Traceroute теряет пакеты ещё до достижения целевой AS
- RIPE RIS / BGP-мониторинг показывает изменение анонсов
- Проблема наблюдается для всего диапазона IP ASN, не одного адреса
- Сторонние AS (за рубежом) видят ресурс нормально

---

### 2.7 Замедление (Throttling)

**Как работает.** ТСПУ не блокирует, а ограничивает пропускную способность до уровня, делающего ресурс практически недоступным. Применялось против Twitter в 2021 году.

**Признаки:**

- TCP-соединение устанавливается, TLS проходит
- HTTP-ответ начинает поступать, но крайне медленно (единицы кбит/с)
- Размер окна TCP принудительно занижен
- RTT нормальный, но throughput деградирован в 100–1000 раз
- Другие сайты через того же провайдера работают с нормальной скоростью

---

### 2.8 Блокировка VPN и прокси-протоколов

**Как работает.** ТСПУ классифицирует трафик по сигнатурам и паттернам:

- OpenVPN: характерное TLS-рукопожатие + UDP паттерны
- WireGuard: фиксированная структура UDP-пакетов
- Tor: fingerprint на уровне TLS + специфичные IP guard-узлов
- Shadowsocks / VMess: анализ энтропии (высокая энтропия = зашифровано)

**Признаки:**

- Соединение устанавливается, первые пакеты проходят, затем обрыв
- Характерная задержка: ТСПУ «ждёт» достаточно данных для классификации
- Протоколы с рандомизацией трафика (obfs4, VLESS с padding) проходят лучше

---

### 2.9 Геоблокировка (самоблокировка сервисов)

**Как работает.** Сервис сам блокирует российские IP по GeoIP. Технически не является государственной блокировкой, но с точки зрения пользователя — недоступность.

**Признаки:**

- TCP-соединение устанавливается, TLS проходит
- HTTP 403 с телом типа «Not available in your region» или редирект
- С зарубежного IP тот же ресурс доступен
- DNS, IP и маршрутизация полностью исправны

---

### 2.10 Временные блокировки

Применяются на ограниченный период:

- **Во время протестов и выборов** — замедление или блокировка Twitter, Facebook, Instagram, TikTok
- **По решению суда с исполнением** — блокировка активируется после вступления решения в силу
- **Точечные блокировки конкретного контента** — отдельная страница или материал без блокировки домена
- **Аварийные блокировки** — по запросу силовых структур без судебного решения

Признаки временных блокировок не отличаются от постоянных — важна корреляция по времени и регионам.

## 3. Что собирают обсерверы

Каждый обсервер — это бинарник (Linux) или APK (Android), развёрнутый в конкретном регионе у конкретного провайдера. Задача: собрать полный набор измерений по целевому URL и вернуть структурированный результат.

### 3.1 DNS-измерения

```
Собрать:
- Резолюция через системный DNS (провайдерский)
  → IP-адреса, TTL, тип ответа (A/AAAA/NXDOMAIN/SERVFAIL)
- Резолюция через 8.8.8.8 (Google)
- Резолюция через 1.1.1.1 (Cloudflare)
- Резолюция через 9.9.9.9 (Quad9)
- Сравнение результатов всех резолверов

Сигналы:
- Несоответствие провайдерского DNS и публичных → DNS-спуфинг
- NXDOMAIN от провайдера при корректном ответе от публичных → DNS-блокировка
- IP заглушки (известные диапазоны страниц-блокировщиков)
```

### 3.2 TCP-измерения

```
Собрать для каждого IP из DNS (порты 80 и 443):
- Результат SYN (success / timeout / RST)
- Время до SYN-ACK (RTT)
- Получен ли RST после установки соединения

Сигналы:
- Timeout → IP-блокировка или BGP blackhole
- RST немедленно → активное отклонение (firewall)
- RST после данных → DPI RST-инъекция
```

### 3.3 TLS-измерения

```
Собрать:
- Успех TLS-рукопожатия (да/нет)
- Сертификат сервера (CN, issuer, fingerprint)
- На каком шаге обрыв (после ClientHello / после ServerHello)
- Тест с разными SNI:
  → с корректным SNI целевого домена
  → с пустым SNI
  → с SNI незаблокированного домена (control)

Сигналы:
- RST после ClientHello с целевым SNI, но не с другим → SNI-блокировка
- Подменный сертификат → MITM (редко, но бывает)
- Рукопожатие зависает на стадии Certificate → throttling
```

### 3.4 HTTP/HTTPS-измерения

```
Собрать:
- HTTP: GET / с заголовком Host: target
  → код ответа, заголовки, первые 4KB тела
- HTTPS: GET / после TLS
  → код ответа, заголовки, первые 4KB тела
- Сравнить с контрольным запросом (с другого IP / через другой резолвер)

Сигналы:
- 403/451 с телом заглушки → блокировка с редиректом
- Тело содержит fingerprint РКН или провайдера
- Код ответа отличается от ожидаемого (из контрольного измерения)
```

### 3.5 Traceroute

```
Собрать:
- Traceroute UDP/ICMP до целевого IP
- Последний отвечающий хоп
- AS каждого хопа (через whois/BGP)
- Точка обрыва

Сигналы:
- Обрыв внутри AS провайдера → IP-блокировка на уровне провайдера
- Обрыв на стыке AS → BGP blackholing выше по цепочке
- Пакеты доходят до цели, но ответа нет → фаервол на стороне сервера (или GeoIP)
```

### 3.6 Измерение скорости (Throttling)

```
Собрать:
- Скачать 1MB данных с целевого сервера, замерить throughput
- Сравнить с throughput к контрольному серверу (заведомо незаблокированный)
- Замерить время до первого байта ответа

Сигналы:
- Throughput < 10% от контрольного → throttling
- Нормальный RTT при аномально низком throughput → подтверждение throttling (не latency issue)
```

### 3.7 Итоговая структура данных от обсервера

Ниже — концептуальный набросок (не выверялся построчно против кода). За
проверенным, актуальным на каждое поле JSON-примером и таблицей "какое поле
чем реально заполняется" — [`linux_binary/README.md`, разделы "Probe result
format" и "Field reference"](https://github.com/RCAgen1/linux_binary/blob/main/README.md#probe-result-format).
Основные отличия реального формата от наброска ниже: `dns.*.addrs` (не
`answers`), `isp_returns_block_ip` (не `_block_page`), четыре DNS-резолвера
включая Quad9, `traceroute.hops` — массив хопов (не число), нет
`last_hop_asn`, `throttle_ratio` (не `throttling_ratio`).

  "timestamp": "2026-06-20T10:00:00Z",

  "dns": {
    "isp_resolver": { "answers": ["1.2.3.4"], "type": "A", "ttl": 300 },
    "google_8888": { "answers": ["5.6.7.8"], "type": "A", "ttl": 300 },
    "cloudflare_1111": { "answers": ["5.6.7.8"], "type": "A", "ttl": 300 },

## 5. Как симулировать блокировки (для тестирования)

### 5.1 DNS-блокировка

```bash
# В /etc/hosts или через локальный dnsmasq
# Возвращать NXDOMAIN:
address=/target.com/#  # dnsmasq: возвращает NXDOMAIN

# Возвращать IP заглушки:
address=/target.com/0.0.0.0
```

### 5.2 IP-блокировка (iptables)

```bash
# Дроп всех пакетов до IP (timeout — как у провайдера)
iptables -A OUTPUT -d 1.2.3.4 -j DROP

# RST-ответ (активное отклонение)
iptables -A OUTPUT -d 1.2.3.4 -j REJECT --reject-with tcp-reset
```

### 5.3 SNI-блокировка (nftables)

```bash
# nftables с модулем nftables string match (или через OpenWRT)
# Проще: использовать nginx как transparent proxy + SSL inspection для теста
```

### 5.4 Throttling

```bash
# tc (traffic control) — ограничение полосы до целевого IP
tc qdisc add dev eth0 root handle 1: htb default 12
tc class add dev eth0 parent 1: classid 1:1 htb rate 1000kbit
tc filter add dev eth0 protocol ip parent 1:0 prio 1 \
  u32 match ip dst 1.2.3.4/32 flowid 1:1
```

### 5.5 RST-инъекция (симуляция DPI)

```bash
# scapy (Python) — отправить RST после получения ClientHello
# Или использовать nftables REJECT после N байт (не точно, но для теста достаточно)
iptables -A OUTPUT -d 1.2.3.4 -p tcp --dport 443 \
  -m connbytes --connbytes 200:600 --connbytes-dir original \
  --connbytes-mode bytes -j REJECT --reject-with tcp-reset
```

## 6. Как агенту различать похожие блокировки

Некоторые типы сложно различить по одним только сигналам обсервера. Агент должен комбинировать технические данные с контекстом из базы знаний.

### 6.1 Throttling vs технический сбой

- **Throttling:** RTT нормальный, throughput аномально низкий, наблюдается только у одного или нескольких ISP, коррелирует с известными событиями (протесты, выборы).
- **Технический сбой:** RTT высокий или packet loss, наблюдается у всех ISP, нет корреляции с событиями.

### 6.2 IP-блокировка vs BGP blackhole

- **IP-блокировка:** traceroute доходит до AS провайдера и обрывается внутри неё. Другие IP того же сервера могут быть доступны.
- **BGP blackhole:** traceroute обрывается на транзитных AS ещё до провайдера. Все IP данного ASN недоступны. Виден в RIPE RIS/BGPmon.

### 6.3 DNS-блокировка vs домен не существует

- Сравнение с публичными DNS: если `8.8.8.8` и `1.1.1.1` возвращают корректный IP — DNS провайдера подменён.
- DNSSEC-проверка: если DNSSEC не проходит на провайдерском резолвере, но проходит через внешний — подтверждение подмены.

### 6.4 SNI-блокировка vs проблема сервера

- Тест с пустым SNI или со SNI незаблокированного домена через тот же IP.
- Если TCP и TLS без SNI работают, а с целевым SNI — RST, это SNI-блокировка.

### 6.5 GeoIP vs государственная блокировка

- Измерения с зарубежных обсерверов: если с зарубежного IP сервис доступен, а ответ HTTP 403 с содержимым «region» — GeoIP.
- Государственная блокировка: проблема наблюдается на сетевом уровне (TCP/DNS), а не на уровне HTTP.

### 6.6 Роль базы знаний (Knowledge Agent)

Когда технические данные неоднозначны, агент обращается к базе знаний:

- **Новости о протестах / выборах** → выше вероятность политической блокировки
- **Новости о решениях РКН** → выше вероятность официальной блокировки по реестру
- **Новости о проблемах провайдера** → выше вероятность технического сбоя
- **Известные паттерны по домену** (ранее был заблокирован) → использовать исторические данные
- **Одновременные проблемы у нескольких несвязанных сервисов** → вероятно инфраструктурная проблема, не блокировка

## 7. Обход блокировок (для контрольных измерений)

Обсерверы должны уметь сделать запрос в обход блокировки, чтобы получить «эталонный» ответ — что возвращает сервер без ограничений.


| Метод                       | Что обходит                   | Ограничения                                          |
| --------------------------- | ----------------------------- | ---------------------------------------------------- |
| Публичный DNS (8.8.8.8)     | DNS-блокировку                | Не поможет при IP-блокировке                         |
| DoH / DoT                   | DNS-блокировку + подмену      | ТСПУ может блокировать DoH-провайдеров               |
| VPN до зарубежного узла     | Всё, кроме полного отключения | VPN-протоколы могут быть заблокированы               |
| Tor                         | Большинство блокировок        | Tor-guard IP частично заблокированы; нужны bridges   |
| WARP (Cloudflare)           | DNS + часть IP-блокировок     | Может быть заблокирован сам                          |
| Использование IP напрямую   | DNS-блокировку                | Не работает с SNI-блокировкой и виртуальными хостами |
| ECH (Encrypted ClientHello) | SNI-блокировку                | ТСПУ может блокировать ECH-трафик целиком            |


Для обсервера рекомендуется: делать измерения **с** блокировками (через штатный DNS и сеть) и **без** (через DoH + прямой TCP через зарубежный туннель), и сравнивать результаты.

## 9. Технические сбои (сервис упал или деградировал)

Это самая вероятная причина недоступности в большинстве случаев — важно уметь чётко отделить её от блокировки.

### 9.1 Падение процесса / приложения

**Как проявляется.** Сервер живой, порт недоступен или отвечает ошибкой.


| Сигнал                                     | Детали                                                  |
| ------------------------------------------ | ------------------------------------------------------- |
| TCP SYN-ACK получен                        | Сетевой стек ОС жив                                     |
| TCP RST сразу после SYN                    | Порт закрыт (процесс не слушает)                        |
| HTTP 502 / 503                             | Reverse proxy (nginx/caddy) жив, но backend не отвечает |
| HTTP 500                                   | Приложение ответило, но упало внутри запроса            |
| Соединение устанавливается, висит, timeout | Процесс принял соединение, но завис (deadlock, OOM)     |


**Отличие от блокировки:** проблема наблюдается у всех регионов и провайдеров одновременно. DNS и маршрутизация исправны. Traceroute доходит до целевого IP. Зарубежные обсерверы тоже не могут подключиться.

---

### 9.2 Исчерпание ресурсов

**Виды:**

- **OOM (Out of Memory)** — ядро убивает процесс. Симптом: периодические падения и рестарты, HTTP 502/503 на короткое время.
- **Disk full** — запись в лог/БД падает с ошибкой, приложение паникует. HTTP 500 или полный отказ.
- **File descriptor limit** — новые TCP-соединения не принимаются, старые работают. `ulimit -n` исчерпан.
- **CPU overload** — соединения принимаются, ответы крайне медленные. TTFB (Time To First Byte) > 10 сек.
- **Thread/goroutine pool exhausted** — запросы ставятся в очередь, timeout клиента наступает раньше ответа.

**Сигналы для обсервера:**

- TCP устанавливается, HTTP-ответ очень медленный или timeout → перегрузка CPU / pool exhaustion
- TCP RST или соединение сброшено до TLS → исчерпание FD или упавший процесс
- HTTP 503 с заголовком `Retry-After` → сервер сам сигнализирует о перегрузке

---

### 9.3 Проблемы с базой данных

**Как проявляется.** Приложение работает, но не может выполнить запрос.


| Симптом                                                    | Вероятная причина                       |
| ---------------------------------------------------------- | --------------------------------------- |
| HTTP 500 с задержкой 5–30 сек                              | Connection pool к БД исчерпан, ожидание |
| HTTP 500 мгновенно                                         | БД недоступна, приложение падает сразу  |
| Часть эндпоинтов работает (статика/healthcheck), часть нет | БД-зависимые маршруты отказывают        |
| Медленные ответы постепенно нарастают                      | Деградация БД (lock contention, bloat)  |


**Сигнал:** `GET /healthcheck` → 200, `GET /api/data` → 500/timeout. Сервис технически жив, но функционально сломан.

---

### 9.4 Сбой зависимого сервиса (Cascading Failure)

Сервис зависит от внешнего API, кэша (Redis), очереди (Kafka/RMQ) или стороннего сервиса.

**Сигналы:**

- HTTP 502/503/504 с телом содержащим имя зависимости (`upstream`, `gateway`, название сервиса)
- Частичная недоступность: одни функции работают, другие нет
- Проблема у всех регионов одновременно, сеть исправна

---

### 9.5 Неудачный деплой / бэд релиз

**Сигналы:**

- Сервис работал, внезапно перестал — без изменений на сетевом уровне
- HTTP 500 на всех запросах или crash loop (502 с короткими промежутками восстановления)
- Время начала совпадает с deployment window (корреляция в логах / новостях команды)
- Проблема у всех регионов, traceroute до сервера нормальный

---

### 9.6 Плановое обслуживание

**Сигналы:**

- HTTP 503 с заголовком `Retry-After` и/или `Maintenance` в теле
- DNS может перенаправлять на отдельную maintenance-страницу
- Заранее анонсировано на statuspage сервиса (statuspage.io, betteruptime и др.)
- Проблема у всех регионов, начало/конец совпадают с announced window

## 10. Сетевые и инфраструктурные сбои

### 10.1 BGP-инцидент (случайный)

Отличие от намеренного BGP blackholing (раздел 2.6) — здесь причина техническая: misconfiguration, route leak, отзыв анонса.

**Примеры:** Facebook 2021 (самоотзыв анонсов), Cloudflare 2019 (route leak через Verizon).

**Сигналы:**

- Traceroute обрывается на транзитных AS, до цели не доходит
- Весь ASN недоступен, не отдельный IP
- BGP-мониторинг (RIPE RIS, BGPmon) фиксирует изменение анонса
- Проблема у большинства провайдеров мира одновременно
- Восстанавливается само в течение минут–часов

---

### 10.2 Обрыв кабеля / физический сбой

Подводные кабели, магистральные линии, оборудование датацентра.

**Сигналы:**

- Traceroute зависает на конкретном хопе (не AS провайдера, а транзитного узла)
- Высокий packet loss на конкретном сегменте пути
- Аффектированы все сервисы, маршрутизируемые через данную линию
- Географически коррелирует: страдают сервисы в конкретном регионе/датацентре

---

### 10.3 Сбой CDN / облачного провайдера

Сервис работает через Cloudflare, Akamai, Fastly, AWS CloudFront и т.д.

**Сигналы:**

- HTTP 502/503/504 с заголовками CDN-провайдера (`CF-Ray`, `X-Cache`, `x-amz-cf-id`)
- Тело ошибки содержит брендинг CDN («Error 1016», «Cloudflare», «Fastly error»)
- Проблема у всех регионов одновременно
- CDN-статусстраница (status.cloudflare.com и т.д.) подтверждает инцидент
- Traceroute доходит до CDN-узла, дальше не идёт

---

### 10.4 Проблемы DNS-инфраструктуры сервиса

Не путать с DNS-блокировкой провайдера — здесь проблема на стороне самого сервиса.


| Причина                                    | Сигнал                                                       |
| ------------------------------------------ | ------------------------------------------------------------ |
| Истёк домен                                | NXDOMAIN у всех резолверов, whois показывает expired         |
| NS-серверы упали                           | SERVFAIL у всех резолверов                                   |
| Некорректная A/CNAME запись после миграции | IP ведёт на пустой сервер или 404                            |
| DNS propagation delay                      | Разные резолверы возвращают разные IP, новый IP ещё не готов |
| Истёк DNSSEC                               | DNSSEC validation failure у всех резолверов                  |


**Как отличить от DNS-блокировки провайдера:** если NXDOMAIN или SERVFAIL у всех публичных DNS (8.8.8.8, 1.1.1.1, 9.9.9.9) — проблема на стороне сервиса, не провайдера.

---

### 10.5 Истёкший или невалидный TLS-сертификат

**Сигналы:**

- TCP устанавливается
- TLS-рукопожатие завершается, но клиент получает `certificate expired` / `certificate invalid`
- `notAfter` в сертификате в прошлом
- Или: CN/SAN не совпадает с запрошенным hostname
- Или: цепочка сертификатов неполная (промежуточный CA отсутствует)

**Специфика:** это ошибка на стороне сервиса, но браузер/клиент отобразит её как «сайт недоступен». Обсервер должен явно проверять валидность сертификата отдельно от доступности.

---

### 10.6 MTU / PMTUD проблемы

**Как работает.** Path MTU Discovery (PMTUD) предполагает, что ICMP Type 3 Code 4 («Fragmentation Needed») проходит по пути. Если где-то файервол блокирует ICMP — TCP-сессия зависает после установки при передаче больших пакетов.

**Сигналы:**

- TCP SYN-ACK получен, TLS иногда проходит
- Маленькие HTTP-запросы (HEAD, GET небольших ресурсов) работают
- Большие ответы (тело > ~1400 байт) зависают или обрываются
- Traceroute работает (UDP/ICMP маленькими пакетами), но данные не идут

---

### 10.7 NAT и Firewall проблемы

**Виды:**

- **NAT table exhaustion** — провайдер исчерпал таблицу трансляций (CGNAT). Новые соединения отклоняются, существующие работают.
- **Stateful firewall timeout** — долго неактивное TCP-соединение вырезается файерволом, клиент не знает об этом.
- **Firewall rule change** — администратор добавил или изменил правило, заблокировав трафик.
- **Симметричный NAT** — UDP-based протоколы (QUIC, DTLS) не пробиваются через некоторые типы NAT.

## 11. DDoS-атаки

Сервис может быть недоступен из-за атаки, а не блокировки и не собственного сбоя.

### 11.1 Volumetric (L3/L4)

UDP flood, ICMP flood, SYN flood. Забивают канал или исчерпывают CPU сетевого оборудования.

**Сигналы:**

- Высокий packet loss по всему пути до сервера
- Traceroute зависает до достижения цели (канал забит)
- RTT резко вырос на последних хопах
- Проблема у всех провайдеров одновременно
- Другие сервисы в том же датацентре/ASN тоже деградируют

### 11.2 Amplification (DNS, NTP, Memcached)

Атакующий отправляет маленькие запросы с подделанным source IP (IP жертвы), усилители отвечают большими ответами жертве.

**Сигналы:** аналогичны volumetric. Специфично: сервер жертвы может получать трафик даже не отправляя ничего.

### 11.3 HTTP Layer (L7)

Slowloris, HTTP flood, запросы к тяжёлым эндпоинтам.

**Сигналы:**

- TCP устанавливается нормально
- HTTP-соединение зависает (Slowloris — сервер ждёт завершения заголовков, которые никогда не придут)
- HTTP 503 с `rate limit` или `too many connections` в теле
- RTT нормальный, TTFB огромный
- CDN/WAF может поглотить атаку и вернуть 429

## 12. Административные и юридические причины

### 12.1 Приостановка хостинга

**Причины:** неоплаченный счёт, нарушение ToS, жалоба на abuse.

**Сигналы:**

- DNS работает, TCP подключается, HTTP 403/404/410 или redirect на страницу хостинга с текстом «suspended»
- Тело страницы содержит название хостинг-провайдера + «suspended» / «account» / «payment»
- Все домены на этом IP аналогично недоступны

### 12.2 Изъятие домена (Seizure)

Регулятор или суд изымает домен — регистратор переводит NS на свои серверы.

**Сигналы:**

- DNS работает, но возвращает IP государственного/регуляторного сервера
- HTTP-ответ — страница с текстом об изъятии («This domain has been seized»)
- Whois показывает смену NS-серверов на регуляторные

### 12.3 Санкционный комплаенс / OFAC

Хостинг-провайдер или CDN прекращает обслуживание клиента из-за санкций.

**Сигналы:**

- Аналогично приостановке хостинга, но может быть внезапным без предупреждения
- Возможен BGP withdrawal (если провайдер — крупный транзитный оператор)
- Коррелирует с новостями о санкционных изменениях

### 12.4 DMCA / takedown

**Сигналы:**

- HTTP 451 (Unavailable For Legal Reasons) — стандартный код для юридических блокировок
- HTTP 403 с телом, упоминающим «copyright», «legal», «DMCA»
- Специфично для конкретного контента, не всего домена

## 13. Цензура в других странах

Для контекста — аналоги российских блокировок в других юрисдикциях. Технические сигналы идентичны описанным в разделах 2–8.


| Страна / система         | Механизм                                       | Особенности                                                                                    |
| ------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Китай (GFW)**          | DPI, DNS poisoning, IP blocking, BGP filtering | Активная RST-инъекция; блокирует Google, YouTube, FB, Wikipedia; HTTPS без SNI иногда проходит |
| **Иран**                 | DPI (NDRA), DNS filtering, IP blocking         | Временные полные отключения во время протестов (2022); блокирует Instagram, WhatsApp           |
| **Турция (BTK)**         | DNS filtering, URL blocking, IP blocking       | Преимущественно DNS; VPN-трафик замедляется; блокирует Twitter/X периодически                  |
| **ОАЭ**                  | DPI (Etisalat/du), VoIP blocking               | Полная блокировка VoIP (Skype, WhatsApp calls); DPI по SNI                                     |
| **Пакистан (PTA)**       | DNS, IP, URL filtering                         | Централизованный реестр; блокировки часто неточные с коллатеральным ущербом                    |
| **Беларусь**             | DPI, DNS (аналог ТСПУ)                         | Полное отключение интернета во время выборов 2020; тесное сотрудничество с РФ                  |
| **Северная Корея**       | Полная изоляция (Kwangmyong)                   | Внешний интернет только для элиты; все зарубежные ресурсы недоступны по умолчанию              |
| **Казахстан**            | DNS, IP, DPI                                   | Практиковал полное отключение (2022); блокирует часть VPN                                      |
| **Индия**                | DNS, IP (по запросу судов)                     | Точечные блокировки; операторы выполняют по-разному (высокий уровень ложных срабатываний)      |
| **Великобритания (IWF)** | DNS (Cleanfeed)                                | Добровольная фильтрация провайдеров; преимущественно CSAM и пиратство                          |
